# StudyFlow 上线路线图（v2 计划）

> 基线版本：v1.4.0（2026-10-31）
> 编写日期：2026-11-01
> 适用对象：单人开发 + AI 协作
> 本文只描述「要做哪些事、按什么顺序做、做到什么算完成」，不含具体代码。

---

## 0. 现状快照（起点）

| 维度 | 现状 |
|---|---|
| 形态 | Electron 桌面应用，纯本地运行，无服务端 |
| 数据 | sql.js（WASM）落盘到 `%APPDATA%\StudyFlow\studyflow.db` |
| AI | 客户端用用户自己的 DeepSeek Key 直连 `api.deepseek.com`（BYOK），Key 经 safeStorage 加密 |
| 核心能力 | 目标 → AI 计划 → 每日教案 → 任务勾选 → 检测（7 单选 + 2 轮问答）→ 进度结算 → 复检回退 |
| 质量设施 | `npm run verify`（双 tsc + schema-lint）、`npm run smoke`（58 项，真 Electron、独立数据目录）、截图脚本 |
| 版本管理 | git + semver + tag（v1.0.0 / v1.1.0 / v1.2.0 / v1.3.0 / v1.4.0）+ CHANGELOG + pre-commit 钩子 |
| 缺失 | 无安装包/签名、无自动更新、无账号、无同步、无监控、无隐私文档、无支付 |

**结论**：功能已闭环，缺的是「交付链路 + 账号化 + 运营」。下面按依赖顺序排。

## 1. 先定三个决策（不定这三个，后面全是返工）

| # | 决策 | 选项 | 推荐 | 影响面 |
|---|---|---|---|---|
| D1 | 谁付 AI 费用 | A 纯 BYOK ／ B 纯平台 Key ／ C 双模式 | **C 双模式，先只做 A** | 决定是否需要 AI 网关、计费、风控 |
| D2 | 数据放在哪 | A 纯本地 ／ B 托管数据库同步 ／ C 本地为主+云备份 | **先 A，再 C** | 决定是否需要账号体系、服务器 |
| D3 | 发行地区 | A 海外 ／ B 中国大陆 | **A 海外（免备案）** | 决定是否必须域名+ICP、支付通道 |

> 已确认的两个事实（避免重复讨论）：
> 1. 桌面应用**不需要域名就能分发和更新**（GitHub Releases / Pages 足够）。
> 2. 一旦有服务端，**必须有一个 HTTPS 地址**，但地址可用免费子域（`*.supabase.co`、`*.workers.dev`）；域名只有在「要发找回密码邮件 / 做品牌下载页 / 国内备案 / 上架应用商店」时才需要买（¥60–100/年）。

## 2. 阶段总览

```
P0 打包地基        P1 分发与更新      P2 账号与同步       P3 AI 网关        P4 商业化与运营
(1 周)             (1 周)             (3 周)              (2 周)            (2 周)
安装包能装  ──▶  别人能下载并自动更新 ──▶ 换机不丢数据 ──▶ 平台 Key 可卖 ──▶ 能收钱、能兜底
```

依赖关系：P0 → P1 是硬依赖；P2 与 P1 可并行（P2 不影响本地使用）；P3 必须在 P2 之后（配额要绑账号）；P4 依赖 P2+P3。

**建议节奏**：P0+P1 两周内做完，先把「可下载的 v2.0 安装包」发出去验证留存；有人真的每天用，再做 P2。

## 3. 分阶段任务清单（按执行顺序）

### P0 · 打包地基（预估 3–5 天）

目标：能产出一个别人能双击安装、卸载、数据不丢的 Windows 安装包。

| 编号 | 任务 | 关键点 | 验收 |
|---|---|---|---|
| T0.1 | 安装 `electron-builder` 并写 `build` 配置 | 当前 `package.json` 的 `dist` 脚本已写 `electron-builder --win --dir`，但依赖没装，等于坏的 | `npm run dist` 能产出 `out/dist/*.exe` |
| T0.2 | 配置 appId / productName / 图标 / 版权 | `appId` 一旦确定不要再改（更新地址与之绑定） | 安装后开始菜单图标正常 |
| T0.3 | 产出两种包：NSIS 安装版 + portable 便携版 | portable 给不想装的人 | 两个包都能启动 |
| T0.4 | 验证用户数据目录 | 安装版 userData 仍是 `%APPDATA%\StudyFlow`；卸载不删数据 | 卸载重装后数据还在（预期行为，需在文档写明） |
| T0.5 | 数据库 schema 迁移回归 | 拿 v1.4.0 的真实库装新版本打开 | 不丢数据、无 `no such table` |
| T0.6 | 冒烟脚本指向打包产物 | 现在 smoke 跑的是源码构建，需新增一条对 `out/` 产物的启动校验 | 打包产物能启动且 `nodes>0` |
| T0.7 | 安装包自检清单 | 数字签名（可选）、杀软误报记录、首次启动耗时 | 记录在 `docs/06-发版检查表.md` |

**进度（2026-11-01，v1.4.0 未升版本号）**

- ✅ T0.1 / T0.2 / T0.3：`electron-builder@26.18.0` + `build` 段（`appId: com.shilingxiaoa.studyflow`、`productName: StudyFlow`、图标 `assets/icon.ico`、`nsis` + `portable`）。`npm run dist` 产出 `release/StudyFlow-1.4.0-setup.exe`（127.1 MB）与 `release/StudyFlow-1.4.0-portable.exe`（111.1 MB），另有 `latest.yml` + `*.blockmap`（`electron-updater` 用）。

### P1 · 分发与自动更新（预估 5–7 天）

目标：陌生人在 GitHub 上能下载、能收到新版本提示、你发版只需一条命令。

| 编号 | 任务 | 关键点 | 验收 |
|---|---|---|---|
| T1.1 | 决定仓库公开/私有 | 公开=免费 CI+社区；私有=需注意 Actions 分钟数 | 仓库可访问 |
| T1.2 | 写 `.github/workflows/release.yml` | tag 推送触发：装依赖→verify→smoke→build→打包→上传 Release | 推 tag 后自动产出 Release 附件 |
| T1.3 | 接入 `electron-updater` | `publish` 指向 GitHub；`autoDownload=false`，设置页给「发现新版本」+手动更新按钮 | 旧版本启动后能看到更新提示 |
| T1.4 | 更新失败兜底 | 校验失败/断网时不能把应用搞坏；保留上一版本回滚路径 | 断网启动不崩、能继续用旧版 |
| T1.5 | GitHub Pages 下载页 | 一句话介绍 + 两个下载按钮 + 版本号 + 更新日志链接 | 手机/电脑都能打开 |
| T1.6 | 设置页显示当前版本与更新状态 | 复用 `layout.tsx` 的 `APP_VERSION`，改为从 `app.getVersion()` 读 | 版本号与实际一致 |
| T1.7 | 错误上报（可选但推荐） | Sentry 或自建最小上报（只上报异常栈，不含学习内容） | 崩溃能在后台看到 |

**验收定义（P1 done）**：一台干净 Windows 机器，从下载页点下载 → 安装 → 填 Key → 生成计划，全程无人工干预。

### P2 · 账号与同步（预估 3 周）

目标：换电脑不丢数据；为 P3 的配额与计费提供身份。

**前置**：D2 决策为 B/C。推荐 Supabase（托管 Postgres + Auth + RLS，免费档够前 100 用户）。

| 编号 | 任务 | 关键点 | 验收 |
|---|---|---|---|
| T2.1 | 建 Supabase 项目（海外 region） | 记录 `project URL` / `anon key`，后者可进客户端，前者写成可配置 | 能用官方 SDK 连上 |
| T2.2 | 设计服务端表结构 | 与本地同构：`goals/plans/days/tasks/lessons/exams/questions/recitations/progress_events/materials`，统一加 `user_id`、`rev`、`deleted_at`、`updated_at` | 表建好、索引齐全 |
| T2.3 | 写 RLS 策略 | 每张表 `user_id = auth.uid()`，禁止跨用户读写 | 用两个测试账号互相访问返回空 |
| T2.4 | 客户端登录 | 邮箱验证码或邮箱密码；登录态 JWT 存 safeStorage | 重启应用免登录 |
| T2.5 | 同步协议（核心） | 见 §6：`progress_events` 只追加；其余实体按 `updated_at` 后写胜；删除用墓碑 | 两台设备能收敛到一致 |
| T2.6 | 首次登录上传本地库 | 幂等：同一设备重复上传不产生重复行 | 重复登录不翻倍 |
| T2.7 | 离线队列 | 断网时写本地，联网后批量推送；冲突按 §6 规则 | 断网 1 小时后恢复能同步 |
| T2.8 | 注销与导出 | 注销=删服务端数据（含级联）；导出=全量 JSON/Markdown | 注销后登录查不到数据 |
| T2.9 | 未登录可用 | 未登录仍是纯本地模式，功能不降级 | 不登录能完整走完一天 |
| T2.10 | 双设备端到端验证 | A 机做 Day、B 机看到进度；B 机检查、A 机看到分数 | 通过 |

**风险**：同步是这类应用最容易埋雷的地方。**不要做实时协作**，只做「后写胜 + 事件追加」；宁可慢 30 秒同步，也不要出现进度反复横跳。

### P3 · AI 网关（预估 2 周）

目标：支持「平台 Key」模式——用户不填 Key 也能用，你按额度收费；同时不破坏 BYOK。

| 编号 | 任务 | 关键点 | 验收 |
|---|---|---|---|
| T3.1 | 网关骨架（Cloudflare Worker 或等价） | 只做 `/ai/plan`、`/ai/lesson`、`/ai/exam`、`/ai/grade`、`/ai/ask` 五个转发端点 | 用 JWT 能调通一次 |
| T3.2 | JWT 校验与用户识别 | 复用 P2 的 Supabase JWT（校验公钥） | 无 token/伪造 token 返回 401 |
| T3.3 | 配额与限流 | 每用户每日调用上限、每分钟频率上限；超限返回明确错误码 | 压测能触发 429 |
| T3.4 | 计量与账单 | 每次调用记录 tokens/成本到服务端（表结构照搬本地 `ai_usage`） | 月度成本可按用户汇总 |
| T3.5 | 流式与超时 | 转发保持 SSE/流式；总超时 > 客户端超时 | 长响应不中断 |
| T3.6 | 客户端 AI 层抽象 | 把 `ai/client.ts` 改成 provider 接口：`byok` / `gateway` 两种实现，设置里可切 | 两种模式都能完整跑完检测 |
| T3.7 | 额度用尽引导 | 网关返回额度错误时，弹窗引导「切换到自己的 Key」+ 跳设置页 | 引导路径可达 |
| T3.8 | 滥用防护 | 单请求 token 上限、异常高频冻结、内容安全兜底 | 构造异常请求被拦截 |
| T3.9 | 条款核对 | 读 DeepSeek 服务条款，确认「代用户调用」是否允许；不允许则只保留 BYOK | 记录结论到本文档 |

**成本口径**：检测约 ¥0.02–0.03/次、备课 ¥0.013/天、计划 ¥0.025/份。一个每天学一天的活跃用户约 ¥1–2/月，**定价必须高于这个数**。

## 4. 技术选型（推荐值）

| 层 | 推荐 | 备选 | 说明 |
|---|---|---|---|
| 打包 | electron-builder | electron-forge | 与现有 electron-vite 兼容，配置量最小 |
| 更新 | electron-updater + GitHub Releases | 对象存储 + 自写检查 | GitHub 零成本 |
| 账号/数据库 | Supabase（Postgres + Auth + RLS） | Neon + 自写 Auth；阿里云 RDS（需备案） | 免费档够起步 |
| 网关 | Cloudflare Workers | Vercel Functions / Railway | 免费额度大、边缘、冷启动短 |
| 监控 | Sentry（错误）+ UptimeRobot（存活） | Better Stack | 都有免费档 |
| 分发页 | GitHub Pages | Cloudflare Pages | 零成本 |
| 代码签名 | 暂缓（下载页说明）→ 有收入后买 | Azure Trusted Signing | SmartScreen 影响转化 |

**明确不建议**：自建 VPS 单机跑 Postgres 作为唯一数据副本（单点故障 + 备份不可验证 + 运维时间成本高）。

## 5. 成本模型（人民币/月）

| 规模 | 托管 DB | 网关 | 存储/带宽 | 域名 | AI 成本（平台模式） | 合计 |
|---|---|---|---|---|---|---|
| 0–100 用户 | ¥0（免费档） | ¥0 | ¥0 | ¥0 | 按实际，约 ¥0–200 | **¥0–200** |
| ~1000 活跃 | ¥70（Pro） | ¥0–70 | ¥20 | ¥6 | 约 ¥1000–2000 | **¥1100–2200** |
| ~5000 活跃 | ¥70–300 | ¥70 | ¥50 | ¥6 | 约 ¥5000–10000 | **¥5200–10400** |

> 结论：**基础设施成本几乎可以忽略，真正的成本是 AI 调用**。所以定价必须按 AI 用量设计，且必须提供 BYOK 让重度用户自己承担。

## 6. 同步协议要点（P2 的技术核心）

1. **事件不可变**：`progress_events` 只追加、不修改、不删除（除非注销），天然无冲突。
2. **实体可覆盖**：`goals/plans/days/tasks/lessons` 按 `updated_at` 后写胜；同毫秒冲突用 `device_id` 字典序决胜。
3. **删除用墓碑**：`deleted_at` 非空即删除，30 天后物理清理。
4. **进度不存百分比**：与现在一致，进度永远由事件 + 实体状态推导，避免同步后「进度对不上」。
5. **拉取增量**：客户端保存 `last_pulled_at`，`where updated_at > last_pulled_at`。
6. **服务端不自作主张**：服务端不重算出题/评分，只做存储与转发，保证与本地逻辑一致。

## 7. 发布流程（每次发版照做）

1. 改功能 → `npm run verify` → `npm run smoke`（必须 58/58 或更新后的全绿）。
2. 更新 `CHANGELOG.md`（新版本段落，写「变化/影响/迁移」）。
3. 同步升两处版本号：`package.json` 的 `version`、`src/renderer/components/layout.tsx` 的 `APP_VERSION`。
4. 提交：`feat: ...（vX.Y.Z）`；打 tag：`vX.Y.Z` 并写附注。
5. 推 tag 触发 CI → 产出安装包 → GitHub Release 附件。
6. 下载页更新版本号与「更新了什么」。
7. 若涉及数据库结构：必须验证「老库升级不丢数据」（T0.5）。

**版本号规则**：新增功能 → 次版本；纯修复 → 修订号；破坏性数据结构变化 → 主版本，并在升级时自动迁移（参考 v1.3 的 `locked → learning` 迁移写法）。

## 9. 里程碑时间表（以周为单位，可压缩）

| 周 | 目标 | 里程碑 |

| W1 | P0 打包 | 本地能产出 NSIS 安装包，干净机器可装 |

| W7–W8 | P4 商业化 | 定价页、开通流程、隐私文档、备份演练、监控 |
| W9 | 公开发布 | v2.0.0 发布 + 下载页 + 一条发布说明（含成本与隐私说明） |

> 如果只有周末时间，按 2 倍时长估算；但**顺序不能变**：先 P0/P1 拿到真实用户反馈，再决定 P2 投入多少。

## 10. 现在就能开始的 5 件事（Top 5）

1. 装 `electron-builder`，把 `npm run dist` 修好，产出第一个安装包（半天）。
2. 在一台干净电脑上走一遍「下载→安装→填 Key→生成计划」（半天，会暴露一堆环境问题）。
3. 写 `.github/workflows/release.yml`，实现「推 tag 自动出包」（1 天）。
4. 接 `electron-updater` + 下载页（1–2 天）。
5. 把这三步的坑记进 `docs/06-发版检查表.md`（持续）。

做完这 5 件，你就有了「能被别人安装、且能持续更新」的 v2，故事才刚开始。

## 附录 A：本次讨论的结论快照

- 桌面应用不需要域名即可分发与更新（GitHub Releases/Pages）。
- 有服务端时必须有 HTTPS 地址，但可用免费子域；域名仅在「发信/品牌页/国内备案/上架商店」时需要。
- 不要自建单机 Postgres 作为唯一副本；优先托管 + 定期导出 + 恢复演练。
- 架构上以「离线优先」为主，本地 sql.js 既是主存储也是容灾副本。
- 收费模式建议「免费 BYOK + 付费平台 Key」，按成功调用计量。
